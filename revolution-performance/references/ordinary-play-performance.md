# 沿普通游玩查性能

## 先固定玩家路径与可比较窗口

**主验收从正常入口、真实操作和真实阵容取得。** 选关、出牌、常态交火、留子后的下一回合、Boss 施法、交接和退出各有不同负载。空格多的开局可能要做更多 AI 试算，满盘能量密度高也可能走固定攻击路径。把固定压力作为吞吐上限和峰值回归。为两组分别采集证据。

- 记录包、设备、图形后端、实际刷新率和绘制尺寸。固定可复现的战术与起始条件，通过玩家共用入口执行。需用 GM 加速结算时，安排在计时窗外，记录其对下一回合存活名单的影响，开窗前清除。
- 同一 runId 记录开始与结束的真实章回、阶段、棋数、攻击、施法、时长、失焦和错误。退出原阶段的窗保留结果和原因，再补一段完整交火。普通续局与固定负载都检查真实结束规模，固定 48 棋出现增援到 49 时按动态负载记录。
- 同时报平均 FPS、帧间隔 P95/P99、最大值和指定阈值的超线次数。严格小于用原始数值判断。目标调整单列版本、日期和理由。在新门槛下重算原样本时保留原来的评级。
- 同一实际路径用相同前置条件做 A→B→A，次数足够时交换先后。关键画面、触控和规则状态的断言与性能结果一起保留。 [测量方法](measurement.md) · [验收与清理](verification.md)

## 安卓实测怎样拆出不同问题

RevGame 在荣耀 DIO-AN00、Android API 31、Mali-G57 MC2、Vulkan、2388 × 1080 / 60 Hz 的机器上跑六章 60 个有效回合。构建源 `ffdd5c87` 实际请求 60 FPS。56 个窗达到至少 45 FPS，34 个也满足当时 P95 < 30 ms。第 4 章 Boss 平均 48.43 FPS，整帧 P95 为 35.33 ms。第 3、6 章的第 2 回合首窗跨阶段，分别补采 4 秒。这个矩阵要和固定棋盘、其他屏幕刷新条件分别读。 [60 回合与构建证据](https://github.com/Yokino337088/RevGame/wiki/%E5%AE%89%E5%8D%93%E6%99%AE%E9%80%9A%E5%AF%B9%E5%B1%80%E6%80%8E%E6%A0%B7%E5%87%8F%E5%B0%91%E6%85%A2%E5%B8%A7)

RevGame 后续将硬验收线改为平均至少 45 FPS 且 P95 < 40 ms，优先争取 P95 < 35 ms。同一批原始数据重算为 56/60 通过硬线、51/60 同时满足优先线和 FPS 下限。只看 P95 时两者分别是 60/60 和 52/60。记录门槛变更与收益对照各自的证据。

- **看帧率请求和呈现节奏。** Unity 2022.3 安卓的 `targetFrameRate=-1` 默认约 30 FPS。按当前系统刷新率请求高帧策略时，仍需观察实际呈现。60 Hz 漏过一次刷新通常形成约 33.33 ms 的显示间隔。固定档与正式策略分别记。前后台、屏幕档位和热状态变化后重新开始有效窗。 [Unity 移动帧率](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Application-targetFrameRate.html) · [Android 帧节奏](https://developer.android.com/games/sdk/frame-pacing)
- **按设备实际像素验证档位。** Vulkan 以 0.05 为步进，取接近请求的等比比例。1080 短边要求 720 时直接请求约 0.667，实机取到 0.65，实际是 702。旧代码先保留比例，下一回合因短边低于 720 恢复原生，重复慢帧。下限向上取可用档约 0.70，约 756。读回真实相机像素再保留；同场景、相机和画幅续用，试档无收益回到前一个有效档。保留独立 UI、触屏映射、格线和预警。 [Unity Vulkan 缩放](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/ScalableBufferManager.ResizeBuffers.html)
- **一次只切一个绘制因素。** 同场 81 棋、世界短边 648，第一章背景开→停→开时 GPU P95 是 31.96 → 14.65 → 30.29 ms，第四章为 32.50 → 13.27 → 30.80 ms。固定诊断局约 30 FPS，差值定位背景渲染器，发布画面要带着完整效果复验。主线程计时可能包含等待，设备没有提供的渲染线程或托管分配计数留为缺测。
- **像素检查属于验收。** 材质、纹理引用和棋子数都可以正常，最终画面仍可能因图案由 Shader 生成而变白，或因共用强度归零而丢掉格线。现有资源上保留装饰、轮廓和玩法预警各自的职责。拍真实相机与目标 AB 下的输出，覆盖遮挡、开局、换回合、着色器回退和退出。
- **局部并行看候选规模与总耗时。** 稀疏开局的走位对照按候选分组，每组复用独立试盘。工作线程未领取时调用线程可接手，完成后按原序处理同分，实际占格仍统一提交。Editor 的局部计时应包含派发与合并，后续用同包安卓的正式路径观测对整帧的影响。 [CPU 与缓存](cpu-cache.md)
- **验包信息可追溯。** 记录选定源码、构建报告 Build ID、架构、测试能力、包名、签名和目标 AB 清单。Windows 检出的 CRLF 与云端 LF 有机会造成清单自身字节差异。核对 APK 内清单与选定 Git 文件的内容及检出规则，再按清单逐一验资源 SHA-256。 [Android 真机流程](android-performance.md)

## Windows 和 Web 复用哪些办法

- **复用可见范围与生命周期。** 剧情中只绘制当前需要的内容。相机可以排除被剧情遮住的棋盘、棋子和战斗反馈；逻辑阶段、场景初始化和资源仍由已有流程推进。验开始、正常读完、跳过、取消和回到玩法的首帧，记录真实绘制量和仍可见的画面。
- **按实际新画面复核帧时间。** 省下被遮挡的对象时，原本被它们挡住的背景像素可能完全露出。同一 Windows Editor 剧情回归中，RevGame 第四章绘制调用从 22 降到 13，完整动态背景出现后 GPU P95 从约 4.68 ms 到三个稳态窗的 6.83–6.87 ms。记录绘制量、GPU 时间和整帧各自的方向。 [全天实践与可见范围对照](https://github.com/Yokino337088/RevGame/wiki/81%E6%A3%8B%E6%B5%8B%E5%BE%97%E9%A1%BA%E6%97%B6%E5%AE%89%E5%8D%93%E6%99%AE%E9%80%9A%E5%B1%80%E4%B8%BA%E4%BB%80%E4%B9%88%E8%BF%98%E4%BC%9A%E5%8D%A1)
- **Windows** 在目标独立包核实实际显卡、D3D、VSync、窗口/焦点与 Present 等待。用真实前后台条件度量阶段；Editor 可辅助定位和验证功能。
- **WebGL** 记录 CSS 区域、DPR、drawing buffer 与浏览器回调。对同章同画幅续用已经验证的像素预算，画幅改变与跨章重新观察。浏览器回调、Wasm 游戏工作、GPU 计数可用性分别记录。 [Windows 性能](windows-performance.md) · [WebGL 性能](webgl-performance.md)
