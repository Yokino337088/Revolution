## 〇、它是干什么的

*先花 30 秒建立直觉，再动手写。*

> [!TIP]
> **只学 2 个类就能干活（真的）**
>
> RevScope.Enter(RevDomain.Battle, RevResGroup.Battle);   // ① 进入"战斗"这段时间
> ... 这一局里，任何脚本注册的计时器 / 事件 / 每帧回调，只要没写 owner，都自动算战斗域的 ...
> RevScope.Exit(RevDomain.Battle);                        // ② 一局结束，一行收干净
>
> [RevLogic(RevDomain.Battle)]                            // ③ 没有界面、但要活一局的业务，写成它
> public sealed class DamageBoardLogic : RevLogicBase { }
> RevLogic.Start<DamageBoardLogic>();                      // Stop 时自动解绑它注册的一切，通常不用写 OnStop 之外的清理代码
>
> 就这些覆盖 90% 的需求。短小的一次性流程（教程一步、一个弹窗）直接 `using (RevScope.Enter("Step1")) { ... }`。

> **人话** 一个战斗场景从来不是一个脚本写完的：技能脚本起计时器、网络回包订事件、UI 脚本挂每帧刷新……
> 它们散落在几十个文件里，谁也不知道"这一局"什么时候结束。以前的做法是各管各的——各自在 `OnDestroy`
> 里清理自己注册的东西。**但"这一局"本身没有一个`OnDestroy`**：大厅不是哪个脚本的子物体，关不掉。
> 作用域系统就是把"这一局"也做成一个一等公民（`RevScope.Enter` / `Exit`），没人管的注册自动挂靠它，
> 结束时框架按钉死的顺序把账收干净——**所以"忘了传 owner"不再等于泄漏**。

| 它替你解决的问题 | 怎么做的 |
|---|---|
| 一场战斗横跨几十个脚本，没人负责"统一收尾" | **域**本身就是回收边界：`Enter` 开始、`Exit` 结束，期间所有"没写 owner"的注册自动归它 |
| 没有界面、但要活一局的业务（结算统计、引导推进）没处放 | **RevLogic**：声明归属域，域一关自动 `Stop`，`Stop` 时自动解绑它注册的事件 / 计时器 / 每帧回调 / 服务 |
| 清理顺序写反：资源先卸、对象池还端着引用 → 白模 | 9 个回收步骤**顺序钉死**（谁依赖谁，谁后关），业务无法改顺序 |
| 显式写了 owner 的全局对象被域误清 | **显式永远优先**：域只接管"没写 owner"的那部分，写清楚的永远安全 |
| 某一步报错导致后面全没清 | 每一步独立 try-catch，失败只记录进报告，绝不中断后续步骤 |
| 回大厅后内存没降，不知道哪一步没清干净 | `RevScope.LastCloseReport` / `RevScope.Dump()`：谁回收了几个、花了多久、哪步失败，一目了然 |

## 一、3 分钟跑起来（可粘贴）

*长域由"游戏流程"开关；局部段用 `using`。*

```csharp
// ① 长生命周期的域：进战斗 / 回大厅，由状态机或场景加载完成的回调来开关
//    第二个参数 = 关域时要整组回收的资源分组（对象池 + 资源），不需要就省略
RevScope.Enter(RevDomain.Battle, RevResGroup.Battle);

// —— 这一局里，任何脚本注册下面这些东西，只要没写 owner，都自动归战斗域 ——
RevTimer.Every(1f, FlushDamage);                    // 没写 owner：战斗域兜底
RevEvent.AddEventListener(GameEventId.Hit, OnHit);  // 没写 owner：战斗域兜底

// ② 一局结束：9 个步骤按固定顺序全部回收（计时器停、事件摘、面板关、池清、资源卸……）
RevScope.Exit(RevDomain.Battle);

// ③ 短小的、一次写完的局部段（教程一步 / 一次加载 / 一个弹窗流程）：用 using
using (RevScope.Enter("TutorialStep1"))
{
    RevTimer.After(0.5f, HighlightTarget);
    // 出这个 using 块，里面建的东西立刻全清
}
```

> [!NOTE]
> **为什么战斗不能写成一个 `using` 块**
> 一场战斗横跨几十个脚本、几百帧：技能脚本取子弹、网络回包改数据、界面刷血条……
> 它们不是在同一段同步代码里创建的，不可能都写进同一对 `{ }` 里。
> 所以长域（大厅 / 战斗）由"游戏流程"调 `Enter` / `Exit`；`using` 只留给局部、一次写完的段落。

## 二、"我要做 X" 对照表（全部 API）

*左边找需求，右边抄一行。*

|---|---|

| 进入一个局部段，出块自动清 | `using (RevScope.Enter("Step1")) { ... }` |
| 结束一个域 | `RevScope.Exit(RevDomain.Battle)` / 用句柄 `handle.Close()` |

## 三、★ 核心原理：没写 owner 为什么也不泄漏

*这是整个系统唯一需要真正理解的机制，花两分钟看懂，后面都是细节。*

框架里负责"清理"的几个门面，**调用方不传 `owner` 时，各自会去问同一句话**：

```text
RevTimer.Every(1f, cb);                 // 没写 owner → 问一句：RevScope.DefaultNode 现在是谁？
RevEvent.AddEventListener(id, cb);      // 同上
```

`RevScope.DefaultNode` 的答案只有两种：

| 当前有没有域开着 | `DefaultNode` 的答案 | 结果 |
|---|---|---|
| 没有 | `null` | 行为和**完全没有作用域系统时逐字一致**——这是"零破坏"的根基，老代码不用改一行 |
| 有（比如战斗域开着） | 那个域自己 | 这次注册就把"战斗域"当成 `owner` 填了进去 |

域关闭时，框架只要对"域自己"调一遍 `RevTimer.CancelAllOf(域)` / `RevEvent.RemoveAllByOwner(域)`，
刚才那些"没写 owner"的注册就被一网打尽——**全程没有任何额外记账**（不往任何清单里 Add 一次），
所以这条路径**零额外 GC**。

> [!WARNING]
> **显式永远优先，域永远不插手**
>
> ```csharp
> RevTimer.Every(1f, cb, owner: audioManager);   // 显式写了 owner：域看不见它，也管不着它
> ```
> 判据只有一句：**这个东西的生命周期 == 这一局吗？** 不是，就显式写 owner。常见的四种情况：
>
> | 该显式写 owner 的情况 | 为什么 |
> |---|---|
> | 全局常驻对象（网络 / 音效 / 关系链 / 配置） | 它比任何一局都活得久，被域回收是意外 |
> | 跨域订阅（大厅脚本订阅战斗事件） | 域关了不该把你的监听也摘走 |
> | 生命周期长于当前域的公共对象 | 同上 |
> | 后台线程 / 编辑器工具里注册 | 那里根本没有"当前域"这个概念 |
>
> **服务（`RevServices`）永远不会被自动归域**——想让一个服务随域走，必须显式 `owner: RevScope.Current`。
> 这是刻意的：服务是"全局能力"，默认应该活得久，自动归域反而容易出事故。

还有一种写法：**注册时写了显式 owner，但又想让它跟着域一起结束**——用 `Attach`：

```csharp
RevTimer.Every(1f, Refresh, owner: this);   // 显式 owner：不会被域自动兜底
RevScope.Attach(this);                       // 但手动登记到当前域：域关闭时，框架对 this 也会清一遍
```

> [!NOTE]
> **`Attach` 清理的是"这个对象名下按 owner 注册的一切"**：事件 / 计时器 / 每帧回调会被摘，
> 它注册的服务会被注销，如果它是一个界面面板（`RevUIPanel`）还会被自动 `Close`。
> ★ 往**已关闭**或**正在关闭**的域 `Attach` 会被明确拒绝（并说清原因），不会悄悄记到一个永远不会被清理的地方——
> 这通常意味着这段代码在域结束之后才跑，请先用 `RevScope.IsActive("Battle")` 判断。

## 四、RevLogic：不用手写清理代码的业务单元

*"没有界面、但要活一局"的业务——战斗结算统计、新手引导推进、成就检查——以前只能硬塞进某个面板
（于是跟着面板生灭，很别扭）或塞进服务（于是一辈子不死）。RevLogic 就是给它们的家。*

```csharp
[RevLogic(RevDomain.Battle)]                        // 声明：我属于战斗域，战斗域一关我自动 Stop
public sealed class DamageBoardLogic : RevLogicBase
{
    private int _total;

    protected override void OnStart()               // ① 开始：放心订事件 / 起计时器 / 取服务
    {
        Listen<DamageArgs>(GameEventId.DamageDone, OnDamage);   // 基类帮你带好了 owner: this
        Every(0.5f, Flush);                                      // 同上，自动归本 Logic
    }

    protected override void OnTick(float dt) { }    // ② 可选：不重写 = 完全不参与每帧，零开销

    protected override void OnStop()                 // ③ 结束：★ 通常一行都不用写（见下）
    {
        RevLog.Info("本局总伤害 " + _total, "Battle");
    }

    private void OnDamage(DamageArgs a) { _total += a.Value; }
    private void Flush() { /* 定期上报 */ }
}

RevLogic.Start<DamageBoardLogic>();      // 启动（域必须已经 Enter 过，否则明确报错并返回 null）
RevLogic.Stop<DamageBoardLogic>();       // 手动停（也可以不停：域关闭时自动停）
```

> [!TIP]
> **★ 最核心的一条：`Stop` 时自动解绑，顺序固定**
>
> `Stop`（无论是手动调用，还是域关闭时框架自动调用）内部固定按这个顺序执行：
>
> ① 摘掉这个 Logic（`owner: this`）注册的全部事件监听
> ② 停掉它的全部计时器
> ③ 摘掉它的每帧回调、注销它注册的服务
> ④ **最后**才调用你写的 `OnStop()`
>
> 所以只要你在 `OnStart` 里用的是基类的 `Listen` / `Every` / `After`（它们自动带 `owner: this`），
> **一行清理代码都不用写**——"忘记清理"在结构上不可能发生。
> 为什么"先解绑、后 OnStop"：`OnStop` 是"我确定要做的最后一件事"，不该再被自己之前注册的回调打扰；
> 但此时服务 / 资源都还在，`OnStop` 里仍然可以正常使用它们（比如上报结算数据）。

**带启动参数：**

```csharp
[RevLogic(RevDomain.Battle)]
public sealed class GuideLogic : RevLogicBase
{
    protected override void OnStart(object param)   // 重写带参数版本
    {
        var step = (GuideStepInfo)param;
        RevLog.Info("进入引导第 " + step.Index + " 步", "Guide");
    }
}

RevLogic.Start<GuideLogic>(new GuideStepInfo { Index = 3 });
```

**什么东西不该做成 Logic：**

| 这种东西 | 应该用 |
|---|---|
| 有界面、要显示的东西 | `RevUIPanel`（UI 系统有池化 / 层级 / 数据绑定） |
| 全局能力（网络 / 配置 / 音效） | `RevServices` 注册的服务 |
| 纯工具函数 | 静态类 |
| 需要跨局存活的进度数据 | 存档 / 配置服务（域关闭会回收 Logic，数据也跟着没了） |

> [!WARNING]
> Logic 之间不要互相持有引用、也不要互相 `Get` 对方的字段——想通信用事件。
> 另外：声明了域但那个域没开，`Start` 会明确报错并返回 `null`，而不是悄悄挂到别的域上——
> 挂错了域，要么早早被误关，要么永远不被关，两种后果都比"启动失败、看报错"更难排查。

## 五、嵌套 / 暂停 / 变体

### 5.1 域可以嵌套，但只能"自顶向下"关

```csharp
RevScope.Enter(RevDomain.Lobby);
RevScope.Enter(RevDomain.Battle);     // Battle 压在 Lobby 上面

RevScope.Exit(RevDomain.Lobby);       // ★ 关的不是栈顶：Battle 会被先一起关掉（并打警告）
```

> [!WARNING]
> 域只能自顶向下关——否则会出现"子域活着、父域已经死了"的悬空状态（子域里的东西可能还在引用父域的东西）。
> 如果 `Exit` 的时候打了"它上面的 XX 也被一起关了"的警告，说明 `Exit` 的顺序写反了，请检查调用处。

关闭过程中，`RevScope.Current` 会立刻改指向"上一层"：

```csharp
// 假设 Lobby → Battle 两层，Exit(Battle) 触发收尾代码时：
// 结算面板的 OnClose 里顺手起了一个"3 秒后跳转"的计时器 —— 这个计时器现在没写 owner，归谁？
// 答案：归 Lobby（因为 Battle 已经进入 Closing，Current 已经回落到 Lobby）
// 不会出现"结算面板刚弹出来就被当成战斗域的东西一起清掉"的怪事。
```

### 5.2 暂停不是回收

```csharp
RevScope.SetTickEnabled(RevDomain.Battle, false);   // 比如弹出设置面板：战斗暂停
// 此时：对象、事件监听、计时器全都还在；只是"归本域兜底的每帧回调"和域内 RevLogic.OnTick 不再被调用
RevScope.SetTickEnabled(RevDomain.Battle, true);    // 恢复，状态没丢
```

> [!NOTE]
> ★ 计时器不受影响——它是"时间"，不是"帧回调"。倒计时继续走，只是画面和逻辑的每帧推进停了。
> 需要连计时器一起停，就不是"暂停"而是"结束"：用 `Exit`。

### 5.3 变体（A/B 用）

```csharp
[RevLogic(RevDomain.Battle, Variant = "Season")]  public sealed class SeasonBoardLogic  : RevLogicBase { }
[RevLogic(RevDomain.Battle, Variant = "Classic")] public sealed class ClassicBoardLogic : RevLogicBase { }

RevLogic.Variant = "Season";       // 启动时按配置 / 远端开关设一次
RevLogic.Start<SeasonBoardLogic>();   // 允许
RevLogic.Start<ClassicBoardLogic>();  // 拒绝（当前变体是 Season），返回 null 并有明确报错
```

> [!NOTE]
> 这里只做"变体过滤"（不匹配的 `Start` 会被拒绝）。如果你要的是"按接口取、实现随变体换"，
> 请用 `RevServices`（服务定位器本来就是"接口 → 实现"的现成机制），不要在这里再长一套容器。

## 六、实战联动：用状态机管理游戏流程（大厅 / 战斗）

*作用域管"一段时间怎么收"，状态机管"现在在哪段时间"——两者天生一对：**状态就是域，切状态就是开关域**。
"打完一局该清干净"从业务代码里彻底消失，因为它变成了"切状态"这个动作本身。*

### 6.1 对应关系（一张表记牢）

| 状态机动作 | 作用域动作 | 含义 |
|---|---|---|
| 状态 `OnEnter` | `RevScope.Enter(域名)` | 进入"这段时间" |
| 状态 `OnExit` | `RevScope.Exit(域名)` | 离开 → 9 步整域回收 |
| 栈状态机 `Push`（旧状态 `OnSuspend`） | `RevScope.SetTickEnabled(旧域, false)` | 被盖住 → 暂停，**不是回收** |
| 栈状态机 `Pop`（旧状态 `OnResume`） | `RevScope.SetTickEnabled(旧域, true)` | 重新露出 → 恢复 |
| 单状态机 `ChangeTo`（旧状态直接 `OnExit`） | `RevScope.Exit(旧域)` | 平级域的线性流程 |
| 退出登录 / 回主菜单（栈 `Clear`） | `RevScope.ExitAll()` | 全部关掉，自顶向下 |

### 6.2 两种流程形态（选一个，别混）

**A. 线性流程：单状态机 `RevLightFSM` + 平级域** —— Boot → 登录 → 大厅 → 战斗，同一时刻只有一个阶段：

```csharp
public sealed class BattleFlowState : RevLightStateBase
{
    public override void OnEnter()
    {
        RevScope.Enter(RevDomain.Battle, RevResGroup.Battle);   // ① 开战斗域
        RevLogic.Start<BattleBoardLogic>();                     // ② 起战斗业务（一行，不用管停）
    }
    public override void OnExit()
    {
        RevScope.Exit(RevDomain.Battle);                        // ③ 整域回收——业务里没有任何清理代码
    }
}
// 切换：flow.ChangeTo<BattleFlowState>() —— 旧状态 OnExit 先收自己的域，新状态 OnEnter 再开新域
```

**B. 可返回的覆盖式玩法：栈状态机 `RevLightStackFSM` + 嵌套域** —— 大厅常驻底层，进战斗压一层、回大厅弹一层（推荐，与真实游戏结构一致）：

```csharp
public sealed class LobbyFlowState : RevLightStateBase
{
    public override void OnEnter()   => RevScope.Enter(RevDomain.Lobby);
    public override void OnSuspend() => RevScope.SetTickEnabled(RevDomain.Lobby, false);  // 被战斗盖住：暂停≠回收
    public override void OnResume()  => RevScope.SetTickEnabled(RevDomain.Lobby, true);   // 露出来：状态没丢
    public override void OnExit()    => RevScope.Exit(RevDomain.Lobby);                   // 只有退出登录才走到这
}

// 进战斗   = flow.Push(new BattleFlowState())   → Enter(Battle)，大厅域保留在下面
// 结算回厅 = flow.Pop()                          → Exit(Battle) 9 步回收，大厅 OnResume 恢复
// 退出登录 = flow.Clear()                        → 逐层 OnExit，每个域各回各家
```

### 6.3 三条纪律（违反必有报错或诡异 bug）

| # | 纪律 | 为什么 |
|---|---|---|
| 1 | **流程机自己不放进它管的域里**：它要么不注册任何东西，要么全部显式写 owner | 流程机是"开关域的人"，活得比任何域都久——被自己开的域回收等于逻辑自杀 |
| 2 | **每个状态只开 / 只关自己的域** | 域只能自顶向下关：状态 A 的 `OnExit` 去 `Exit` 状态 B 的域，等于随机折叠域栈 |
| 3 | **被盖住用 `SetTickEnabled`，真正离开才用 `Exit`**；域栈深度建议 ≤ 3 | Push 一层就 Exit 一层，回大厅时大厅要全部重建——"栈"就白用了 |

```csharp
RevLog.Info(RevScope.LastCloseReport.ToText());
```

```text

  1 业务单元 RevLogic  3 个  0.05 ms
  2 界面 RevUI  2 个  0.31 ms
  3 每帧回调 RevMono  5 个  0.02 ms

  8 服务 RevServices  0 个  0.00 ms
```

| 排查场景 | 看报告里的哪一项 |
|---|---|
| 怀疑某一步没清干净 | 对应步骤的 `Count` 是不是 0（比如计时器那行一直是 0，说明根本没走兜底路径，多半是显式写了别的 owner） |
| 怀疑有步骤出错 | `HasFailure` 为 `true`，对应步骤 `Failed = true`，`Error` 里是异常文本——★ 某一步失败不影响其它步骤照常执行 |
| 怀疑关闭期间又有代码偷偷注册了东西 | `Stragglers`（第 9 步"兜底扫尾"抓到的数量）。正常应当是 0；不是 0 说明有收尾代码（比如某个 `OnStop`）在域关闭过程中又注册了没写 owner 的东西 |
| 想知道这个域配置的回收分组到底回收了没有 | 第 6 / 7 步如果 `Skipped = true` 且 `Note` 写着"没配置回收分组"，说明 `Enter` 时没传 `RevResGroup`，这两步天生不做事 |

**想看全局情况（不止某一次关闭）：**

```csharp
RevLog.Info(RevScope.Dump());
```

会打出当前域栈（谁在谁上面、是否暂停、挂了几个对象 / Logic）+ 最近一次关闭报告，一次打印就够。

## 八、新手最容易踩的 8 个坑

*每条都有人因此白干半天。*

| # | 坑 | 正解 |
|---|---|---|
| 1 | 以为"没写 owner"就等于没人管 | 域开着时，没写 owner 自动归当前域；域一关就清；真的想让它活得比域久，**显式**写 owner |
| 2 | 战斗场景用 `using` 包一整段 | 战斗横跨几十个脚本、几百帧，不可能写进一对 `{ }`。长域用 `Enter` / `Exit` 由游戏流程开关 |
| 3 | `Exit` 一个不在栈顶的域 | 会把压在它上面的域一起关掉（并打警告）。多半是 `Exit` 顺序写反了，检查调用处 |
| 4 | 想暂停战斗，结果计时器也停了 | `SetTickEnabled` 只管每帧回调和 `RevLogic.OnTick`；计时器是"时间"，不受影响 |
| 5 | 全局单例（网络管理器）注册时没写 owner | 一旦战斗域开着，它会被误判成"归战斗域"，战斗一结束就被摘了监听——全局对象永远显式写 owner |
| 6 | 服务（`RevServices`）以为也会自动归域 | 服务永远不会被自动归域，想随域走必须 `owner: RevScope.Current` 显式登记 |
| 7 | `RevLogic.Start<T>()` 返回 `null` 却没看日志 | 一定有明确报错：域没开 / 变体不符 / 正在关闭中 / `OnStart` 抛异常回滚，看 `RevLog` 输出 |
| 8 | 在某个 Logic 的 `OnStop` 里 `Start` 新的 Logic | 域正在关闭时不接受新业务单元，会被拒绝——这属于"下一阶段"的事，等域关完再启动 |

## 八、没达到预期怎么查（5 分钟定位）

*按顺序排除，每步都能立刻验证。*

| 现象 | 查这里 |
|---|---|
| 域关了，计时器 / 监听还在 | 创建时是不是显式写了别的 `owner`？`RevScope.Dump()` 看这个域的归属对象数量；看关闭报告对应步骤 `Count` |
| `RevScope.Enter` 返回了空句柄 | 域名是不是空字符串？是不是同名域已经开着（默认 `ReenterIsError = true` 会报错）？看 `RevLog` 的具体原因 |
| `RevLogic.Start<T>()` 返回 `null` | 看 `RevLog` 报错：域没开 / 变体不符 / 域正在关闭 / `OnStart` 抛异常——四选一，报错里写得很清楚 |
| 某个对象 `Attach` 了但没被回收 | 是不是往已关闭 / 正在关闭的域 `Attach`？这种情况会被拒绝并报错，而不是静默失败 |
| 关闭时某一步报错，后面步骤是不是也没跑 | 不会——每一步独立 try-catch，看 `LastCloseReport` 里具体是哪一步 `Failed`，其余步骤照常执行 |
| 怀疑关闭过程中又有东西"偷偷"注册 | 看 `LastCloseReport.Stragglers`，不为 0 就说明有收尾代码在关闭期间又注册了没写 owner 的东西 |
| 换个场景 / 重进 Play 之后，上一局的 Logic 还在跑 | 正常不会发生——进 Play 时框架会自动复位；如果仍出现，检查是不是绕开门面直接持有了旧的 Logic 引用 |

### 10.2 验收情况

| 项 | 结果 |
|---|---|
| 工程外行为断言（真实源码链接进独立工程，无 Unity） | **182 / 182 通过**：关闭顺序（尤其"池先于资源"）、失败隔离（某步出错不中断后续）、显式 owner 永远优先、嵌套只能自顶向下、关闭中新注册不误伤当前域、RevLogic 回滚 / 逆序停止 / 变体过滤、暂停不影响计时器、零破坏（没有域时行为与旧版逐字一致）、零 GC |
| 零额外 GC | 有域时"没写 owner"的计时器 / 事件注册，比"显式写 owner"多出的分配 ≈ 0（2 万次实测） |
| `Enter` + `Exit` 一轮成本 | 平均 < 4 KB（这是"每局一次"的成本，不在热路径） |
| 依赖 | `RevTimer` / `RevEventSystem` / `RevServiceLocator`（纯 C# 内核均可工程外单测）；Unity 侧另依赖 `RevUISystem` / `RevPublicMono` / `RevObjectPool` / `RevResourceSystem` |


### 10.3 设计来源

| 解决的问题 | 本框架怎么落 |
|---|---|
| "一局游戏"涉及几十个脚本联动，没有统一的生命周期边界 | 抽出 `RevScope` 这个一等公民：`Enter` / `Exit` 划出一段时间，期间所有模块的"没写 owner"注册自动挂靠它 |
| 显式成本和隐式安全不可兼得 | 两条路径并存：没写 owner → 域兜底（零额外记账）；写了 owner → 域永不插手（显式永远优先） |
| 清理顺序全靠人记，一旦搞反就是资源引用错误 | 9 步顺序钉死在枚举里，业务层拿不到修改入口；"池先于资源"这种关键依赖由框架保证，不再靠口口相传 |
| 没有界面的业务没地方放，要么塞进面板、要么塞进服务 | `RevLogic`：声明归属域，`Stop` 时固定顺序自动解绑一切，`OnStop` 只写业务收尾 |
