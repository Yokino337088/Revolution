〇先让 AI 做什么

日常入口是常驻 RevMCP，CLI 是 AI 执行、CI 与排障的兜底，不要求你先背命令。

直接说“检查当前工程的 RevMCP 调用延迟。记录冷调用、20 次稳态样本和活动窗口开关状态；不要改场景或停止我的 Play。解释卡在 Python、Unity tick 还是动作自身。”
更新要更新两端Python 服务更新后重启对应 MCP 会话；Unity 桥更新后等待编译完成。只换 Python，旧编辑器不会突然拥有新增能力。始终显式选择目标工程。

一调用慢在哪里

不是给轮询数字多减几个零。一次普通查询曾包含三次 Unity 往返和无关图像报告工作。

旧路径
发现全部 Editor → 发现 Play 才有的运行时 → 执行动作 → 每次查询也生成 HTML，扫描共享报告目录。
新路径
按目标查目录 → 普通 Editor 短缓存复用 → 每次真实执行目标动作 → 保留 JSON/日志；测试或本次截图才生成独立 HTML。
改动约束没有消失
Editor 能力说明缓存最多 2 秒以 session、domainId 域代际、Play、暂停、编译、导入状态为键；变更、失败和显式 discover 后失效。Session 继续保留跨重载工单，domainId 单独变化。旧桥没有域字段仍受两秒上限约束。只缓存说明，不缓存业务结果。
Editor 调用不再先查运行时；CLI 会话操作不先查 Editor目标能力仍需真实注册。GM/game 保留本局实时目录校验。
Runtime 工单轮询 5ms → 20ms → 50ms 退让只 GET 同一 request ID；取消/超时仍收尾，绝不重新 POST 变更。不是零延迟承诺。
证据目录按工单隔离普通查询仍保存 JSON 与活动日志；测试计划及本次截图保留 HTML，不拿历史图片冒充当前画面。
Unity 主线程仍是边界空闲 Editor tick、导入、编译、AB/Player 构建及动作自身耗时仍可能占主要时间。没有把 Unity 变更并发化，也没有用第二个 batch Unity 绕过忙状态。

二紧凑工具目录

项目注册了几百项能力时，不必在每次握手把所有工具描述都塞给模型。

可选 --compact-tools 只暴露三个稳定工具：rev_discover、rev_call、rev_run。真实能力没有被删除，AI 按关键词找需要的能力，再通过统一入口调用。默认仍保留全部动态工具，兼容旧配置。

AI / CI 连接参考
以下路径相对仓库根目录。MCP 客户端需要固定路径时使用自己的配置，不写他人的机器路径。
python Revolution.RevMCP/rev_mcp.py --project RevolutionFrameWork_Unity --compact-tools serve
{
  "target": "editor",
  "query": "transform",
  "offset": 0,
  "limit": 20
}

上面的 JSON 是 rev_discover 参数，不是 rev_call 参数。空参数保留旧版完整发现；筛选返回 actionTotal/commandTotal 与分页位置，不丢 unavailable 原因。

紧凑模式 tools/list 不请求 Unity；第一次真正调用仍需连接并发现目标，冷启动要单独统计。需要逐动作按钮式工具列表时，省略该开关。

三批量与计划怎么选

可以少往返，不能把“尚未完成”假装成“同帧完成”。

需求选什么
多个允许的同步检查/编辑batch.call，最多 64 步，默认遇错停止，每步仍校验参数与确认。
点击 → 等界面 → GM → 断言 → 清理rev_run，保留等待、业务后置与 finally。
Play/编译重载/测试/构建/运行时跨帧专用动作和顺序计划，不塞进同步 batch；拒绝原因要保留。
{
  "target": "editor",
  "action": "batch.call",
  "arguments": {
    "steps": [
      {"action": "editor.status"},
      {"action": "scene.list"},
      {"action": "ab.config"}
    ],
    "stopOnError": true
  }
}
禁止“重试”变成重放超时不代表没执行。先查原工单及副作用；不能重新提交新 ID 的删除、点击、GM、构建或资源修改来碰运气。

四活动窗口为什么不卡整页

窗口还是记录目的、参数、结果和 GM；但没必要每个 GUI 事件都重新解释全部记录。

可见记录最近最多 500 条
日志流最近最多 64 个 JSONL 文件
读取预算每次 Poll 共用 256 KiB / 128 行
刷新节奏250ms 检查；无变化不主动持续 Repaint
  • 读取预算属于整次刷新，不再是每文件 256 KiB，积压分批消化，轮转避免单个 Agent 独占。
  • 复用读缓冲、记录文件偏移和时间；未变文件不重复开流解析，半行中文 UTF-8 等下一次补完整。
  • 开始/结束事件合并后缓存标题、用途、原始动作、搜索文本和 GUIContent；筛选改变才重建筛选结果。
  • 缓存文字高度，以累计高度定位视口，只为屏幕内记录创建按钮。详情、复制、GM 识别与清空视图继续保留。
  • OnGUI 不做日志磁盘读取；清空只清视图，不删除原始证据。窗口不通过 MCP 自我查询，不产生日志递归。
实时不等于一帧读完整个历史突发大量日志时分多次刷新追上。预算限制保护编辑器；不能把它说成“无限日志、零 GC”。

editor.activity 同样复用游标并有界补齐（单次最多8批，批间20ms软预算，不含筛选/摘要、不是硬期限）。返回 pending/totalIsFinal/invalidLines/polls/scope；积压时只读重查继续进度，不能拿首批 total 当完整账本。完整性只针对最近64流、新流尾部256KiB、最多500条的当前视图，不覆盖全部历史，半行和无效行不计入total。

六升级与故障排查

先区分 Python 服务版本、Unity 桥版本和实际业务执行耗时。

  1. 更新 RevCLI 与 RevMCP，增量更新目标工程中的 Automation 桥和活动窗口，保留项目自定义接线与生成物。
  2. 等 Unity 编译完成，检查 compilation/Console。重启对应 Python MCP 会话；需要紧凑模式再加 compact-tools。
  3. 让 AI 按关键词发现一个新动作，再查询已存在的只读动作，核对实际返回，不用离线清单宣布升级成功。
  4. 调用仍慢：先测底层与 MCP 两层，再分开窗口开关；长构建、导入和编译可能阻塞主线程，别删证据或强杀用户编辑器。
  5. 目录失效或 session 变化：重新发现；失败不能自动重放。测试计划、取消和 finally 规则不变。
