0. 先搞清一件事：RevMCP 和 Automation 有啥区别？

很多人一上来就懵：仓库里怎么有两个自动化目录？其实它们是上下游，不是两个竞争品。

Revolution.Automation Revolution.RevMCP（本文档）
是什么命令行工具，真正执行动作的那一层MCP 服务，把 AI 的话翻译成动作
谁来用人（命令行）、CI 脚本AI 客户端：CodeBuddy、Codex、Claude 等
入口rev.py / rev.cmdrev_mcp.py … serve（stdio 协议）
能做的事125 个编辑器/打包/导表/GM 动作上面这些 ＋ 游戏运行时（UI、状态、截图、业务接口）
依赖关系不依赖 RevMCP内部调用 Automation 去执行 Editor 动作
配置成本零（Python 3.10+ 直接跑）要在 AI 客户端里配一次 MCP
你得到什么一条命令的结果一句自然语言的测试结论 + 证据
你说：帮我测一下战斗能不能打起来
        ↓
   AI（CodeBuddy / Codex）+ Skill
        ↓  调用 MCP 工具
     RevMCP（本文档）───→ 游戏运行时能力（UI 点击、GM、断言、截图）
        ↓
   Revolution.Automation（真正干活的命令行）
        ↓

新手该先用哪个？

你的目的 建议
只是想看看 Unity 现在什么状态、跑一次打包/导表用 Automation，一条命令，不用配任何东西
想让 AI 帮你测功能、自动截图、写测试报告用 RevMCP
接 CI（Jenkins / GitHub Actions）跑固定流程用 Automation（CI 里不需要 AI）
完全不熟悉命令行，只想像聊天一样操作用 RevMCP（但建议先让工具跑通一次 doctor）

推荐路径：先按 Revolution自动化工具使用说明 跑通 doctor 和 editor status，确认“命令能驱动 Unity”这件事成立；再回来配 MCP。这样出问题时你能分清是“底层不通”还是“AI 那边配错”。

1. 3 分钟接线（以 CodeBuddy / Codex 为例）

MCP 服务就一条命令，本质是让客户端在后台启动它：

python <本仓库绝对路径>/Revolution.RevMCP/rev_mcp.py --project <Unity 工程绝对路径> serve

⚠️ 两个 &lt;…&gt; 是占位符，必须换成你自己机器上的绝对路径。MCP 客户端只接受绝对路径，这是客户端的硬要求，不是文档偷懒。文档不会写死任何人的机器目录。

CodeBuddy（~/.codebuddy/mcp.json）：

{
  "mcpServers": {
    "revolution": {
      "type": "stdio",
      "command": "<Python 3.10+ 安装目录>/python.exe",
      "args": ["<本仓库绝对路径>/Revolution.RevMCP/rev_mcp.py",
               "--project", "<Unity 工程绝对路径>", "serve"],
      "env": { "PYTHONUTF8": "1", "PYTHONIOENCODING": "utf-8" },
      "description": "Revolution RevMCP：操作 Unity 编辑器与游戏运行时"
    }
  }
}

填完在 MCP 面板点 Try to Run，绿灯即成功。不需要重启 IDE。

Codex（~/.codex/config.toml）：

[mcp_servers.revolution]
command = '<Python 3.10+ 安装目录>/python.exe'
args = ['<本仓库绝对路径>/Revolution.RevMCP/rev_mcp.py', '--project', '<Unity 工程绝对路径>', 'serve']
startup_timeout_sec = 60
tool_timeout_sec = 300

[mcp_servers.revolution.env]
PYTHONUTF8 = '1'
PYTHONIOENCODING = 'utf-8'

验证：codex mcp get revolution，能看到 enabled: true 和正确的 args 就对了。

为什么要写死绝对路径？ 客户端是被别的程序（IDE/终端）拉起来的，工作目录不可控，相对路径会指到别的地方。所以这里必须绝对路径，正文其它地方一律用相对路径。

2. 接上之后先说这三句话（渐进式）

不要一上来就让它跑完整回归。按这个顺序：

第 1 句——确认能连上：

用 revolution 的 rev_discover 列出所有可用动作，告诉我一共多少个，并挑 3 个和编辑器状态相关的给我看。

第 2 句——确认能操作编辑器：

用 rev_call 调 editor.status，把 playing、compiling 报给我。

第 3 句——确认能操作游戏：

进入 Play，调 gm.list 看看有哪些 GM 指令，然后停掉。

三句话都通了，再让它测真实业务。

3. 三个稳定工具（AI 最常用的就这三个）

工具清单会变（当前 124 个），但下面三个是稳定钉子，名字永远不变：

工具 干什么 类比
rev_discover列出真实可用的动作、参数、环境要求先看菜单有什么菜
rev_call调一个具体动作（target + action + 参数）点一道菜
rev_run跑一份多步计划（准备→执行→断言→清理）点套餐

其余一百多个工具是按动作动态生成的，名字后面带一串哈希（例如 editor_ab_build_d76143ddf55a0617）。它们能用，但不适合让 AI 去记忆——优先让 AI 用 rev_discover + rev_call，这样接口变了也不会失效。

4. 让 AI 测你自己的游戏功能（关键一步）

AI 不可能凭空知道你的“背包加道具”怎么查。你得给游戏注册能力，AI 才有东西可调：

// 在游戏侧登记一个可被自动化的业务能力（名称由你定）
RevRuntimeAutomation.Register("inventory.count", () => bag.Count);
RevRuntimeAutomation.Register("inventory.add", args => bag.Add(args.GetInt("id"), 1));
RevRuntimeAutomation.Register("inventory.reset", () => bag.Clear());

登记之后，AI 才可以说：

记录背包数量 → 加一个道具 → 断言数量 +1 → 截图 → 复位归零。

这就是 RevMCP 的边界：它负责“发现 + 调用 + 断言 + 证据”，业务接口必须由项目提供。工具不会猜你的游戏逻辑。

5. 常见问题（新手 90% 卡在这几条）

现象 原因 怎么办
AI 说「没有在线 Unity 桥接」Unity 没开 / 还在编译 / 工程路径不对打开工程等编译完；核对 --project
客户端里看不到 revolutionJSON 写错（少逗号、BOM）或路径不存在用 python &lt;路径&gt;/rev_mcp.py --project &lt;工程&gt; discover 手动验证能否跑
能发现动作，但一执行就失败动作要求 Play 模式 / EditMode看动作的 environment 字段，先切到正确模式
AI 跑完说“成功”但游戏没变缺断言——它只调了动作，没验证结果明确要求“断言 + 截图”，别只说“点一下”
中文路径报错Python 默认编码不是 UTF-8配置里加 PYTHONUTF8=1
想用 WebGL 包做自动化不支持WebGL 没有本机 HTTP 能力，只能用编辑器或开发版 Player

6. 它做不到什么（提前说清，省得你试）

  • 不能凭空理解未注册的业务：没登记查询/动作/复位，AI 只能“点按钮”，无法断言业务结果；
  • WebGL 构建不支持运行时测试接口；
  • 正式发布的包默认不含这些接口，只在 Development Build + 显式开启时存在；
  • 两个 MCP 连接不能同时改同一个工程（比如 Unity MCP 和 RevMCP 同时操作）；
  • 断言失败、清理失败都会被记为失败——这是故意的，避免“跑完看起来绿了、其实脏了”。
